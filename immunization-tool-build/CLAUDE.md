# AAP Immunization Tool

Mobile-first web app that helps caregivers track each child's vaccines, understand why each matters, and prepare for pediatrician visits.

**Read `SPEC.md` before writing code.** It is the source of truth for screens, routes, data, behavior and acceptance criteria. Screen numbers (0, 1a, 2, 4c …) are shared with the design team's IA doc and sitemap; keep them in route comments and component names so design and code stay traceable.

## Working rules

- Build in the milestone order in SPEC.md §12. Finish a milestone's acceptance criteria before starting the next.
- Mobile first: design and test at 375px wide, then scale up. Touch targets at least 44px.
- Every user-facing string goes through i18n with complete English and Spanish versions. Language is switched in Settings; never show translation markers or mix languages on screen. No hard-coded copy in components.
- Never hard-code vaccine schedule rules in components. They live in `data/schedule/` and are read by the schedule engine (`lib/schedule/`).
- `data/schedule/aap-2026.json` and `data/vaccines/catalog.json` are built from the AAP 2026 immunization schedule. They are still SAMPLE DATA until AAP's clinical team reviews them.
- `data/fixtures/accounts.json` has 4 sample children (Maya, Leo, Ava, Sofía), one per key scenario, used to seed the mock API and as end-to-end test cases (SPEC.md §5b).
- Keep the `SAMPLE` flag on every seed entry and show a dev-only banner while any sample data is loaded.
- All caregiver and child data is stored on the user's HealthyChildren.org account through the API in SPEC.md §5a. Never store child data in localStorage, sessionStorage, IndexedDB or cookies. Components call `lib/api/`, never `fetch` directly.
- The prototype runs against an MSW mock of that API. External services (AAP My Account, the HealthyChildren.org API, SMS/email, OCR) sit behind interfaces with mock implementations. Do not call real services.
- Child context: any screen that writes data must show which child it writes to (editing banner) and must not let the child change mid-edit.
- Keep the schedule engine pure and unit-tested. Every status rule in SPEC.md §7 needs a test.
- Accessibility: WCAG 2.2 AA. Status is never shown by color alone.

## Commands

- `npm run dev`: start the dev server (MSW mock API starts in the browser; log in with any fixture account)
- `npm test`: unit tests with Vitest (schedule engine, validation, mock API contract, i18n key parity)
- `npm run test:e2e`: Playwright tests for the scenario flows in SPEC.md §11 (375px viewport), plus the axe audit (`a11y.spec.ts`), states and keyboard specs. Starts its own dev server on port 3100, or set `E2E_PORT` to reuse a running one
- `npm run lint`, `npm run typecheck`
- `npm run validate:data`: Zod-validate everything in `data/` (also runs before `npm run build`)

## Decisions that override SPEC.md

- **No Tailwind.** Styling is plain CSS: design tokens are CSS custom properties in `app/theme.css` (the single theme file); components use CSS Modules.
- **Grayscale wireframe.** This is a UX wireframe: no hues in tokens or components. Status is shown with icon + text + border/fill pattern (see `.pill` in `components/shell/shell.module.css`).
- **Logos are the only color.** The HealthyChildren.org logo (`public/brand/healthychildren.svg`) and the AAP logo (`public/brand/aap.png`) keep their own colors; everything else stays grayscale.
- **Header:** the HealthyChildren.org logo with "Immunization Tool", then the child switcher. Mobile: stacked and centered with a rule between them. Desktop (768px+): one row, brand left, switcher right. The header scrolls away; on forms the editing banner sticks to the top instead.
- **Child switcher is a row of pills** (not a dropdown): the selected child is expanded with their first name, the others show their initial (full name for screen readers), on gray fills. Buttons use `aria-pressed`; the list is labeled "Child". With one child it shows just that child's name. Pages without a selector (Home, Settings, signed out) show the brand only. There's no "All" option (the user set it aside for now).
- **Schedule tab** (not in SPEC.md §3): a fifth tab, between Home and Visit Prep, that opens the selected child's page (screen 2, `/child/[id]`), the same page Home's cards open. It's another way in, not a new page. All `/child/…` routes belong to the Schedule tab, so it's the active tab there. With no children it goes to Home.
- **Home (1) layout** (changes SPEC.md §6.1): two separate closable notices (schedule update, flu season) above the title; closing is remembered for the session in the in-memory query cache. The title is "Child Status" (the child cards; Record + replaced the old Add to record button). Each card shows the name, status pill and the next vaccines with their age windows (up to 3, then "+N more"); no age and no "Due now / Overdue / Coming next" title. Below it, "Open Questions" lists open questions by child (only children who have one), each in a Visit Prep–style row with a checkbox to mark it resolved (saved to the account; a checked question stays, crossed out, until Home is left, so it can be unchecked), plus a link to that child's Visit Prep. With no open questions at all it says so. Home has no open-questions button and no "Add a child" (that's in Settings and the empty state).
- **Add to record (4a) is a page, not a form** (changes SPEC.md §6.4a): it shows the child switcher (the child it's for is selected) instead of the editing banner, and no tab bar (route `actionBar: true`); switching child reloads Add to record for that child. The title is "Create a Record for {name}"; Scan a record sits right of it (below it, on the left, when the title fills a phone's width). No "Recently logged" list (only "Due Next for {name}" quick picks). Below the search: "Can't find what you're looking for?" with a short line and a plain "Add a Custom Vaccine" link row (text left, chevron right; not a button). "Cancel" is the only button in the bar fixed to the bottom. Sections are `--space-6` apart; the link is `--text-sm` so it doesn't compete with the heading. The logo footer leaves room for fixed bottom bars (forms and 4a) so it's never hidden.
  - **Opened for one vaccine** (`?vaccine=`, from a vaccine page's Add Record +): no search field, no Scan a record and no Add a custom vaccine (Cancel only), just that vaccine's name and its dose picker (Continue → Dose Edit).
  - **One dose to offer → no dose step:** picking a vaccine with a single dose option (e.g. COVID-19 or flu with nothing recorded) goes straight to Dose Edit, and so does opening 4a with `?vaccine=` for one (replacing 4a in history).
  - **Cancel goes back where 4a was opened from**, passed as `?from=` (checked with `safeNext`): Home's Add Record sends `from=/`, the child page sends its own path, a vaccine page sends `/vaccines/[id]`. Without `from` it goes to the child's page. Switching child keeps `from`, but a `/child/…` value becomes the new child's page.
- **Vaccine Detail (6a) "← Back"** (was "All vaccines") goes back in history (`router.back()`), so it returns to the page and tab it was opened from; opened directly (no earlier in-app page, tracked by `components/shell/inAppHistory.ts`), it links to `/vaccines`.
- **Vaccine Detail (6a) child module:** "Add Record +" (→ Add to record, prefiltered) and "Add a question", which opens Home's Question popup (`QuestionDialog`) with the page's child and vaccine preselected (origin `vaccineDetail`); saving shows the same toast.
- **Dose Edit (4) has no editing banner:** a chip with the child's first name sits above the vaccine name (route `selector: false`; the child is still locked, no switcher, no tab bar). Edit Child (3), Scan (4b), Review Scan (4c) and Custom Vaccine (4d) keep the editing banner.
- **Home quick actions** (`components/home/QuickActions.tsx`): three buttons ("Add Record +", "Appointment +", "Question +") between the notices and Child Status (mobile: Add Record on its own line, the other two side by side; 768px+: one row), each opening a popup (`components/ui/Modal.tsx`, native `<dialog>`: X, Escape and backdrop close it; focus returns to the button).
  - **Add Record**: pick the child, then go to Add to record (4a) for that child. With one child it goes straight there.
  - **Appointment**: child + month/day/year, Cancel/Save, saved in place to `nextAppointment` (same field as Visit Prep; required, valid, not in the past).
  - **Question**: child, optional vaccine, question, Cancel/Save, saved in place.
  - Appointment and Question don't redirect (they show in Visit Prep, and questions on Home): a toast (`components/ui/Toast.tsx`) above the tab bar confirms it, with a link to the child's schedule. It goes away after about 6 seconds (paused while hovered or focused) or with its X.
- **Child page (2) layout** (changes SPEC.md §6.2): the name with "Add Record +" (→ Add to record) and "Print" (→ record export) on the right of the same line, then **Overview / Schedule tabs** (WAI-ARIA tabs; the choice is in the URL as `?tab=schedule` and kept when switching child).
  - **Overview:** counts for Due now / Overdue / Needs info (no Given count), then prompt cards: "Add past vaccines" (no dose records yet) and "School and childcare" (ages 4–6). No "Complete profile" card (dropped; SPEC.md §6.2 has one), and no Settings link for it. Then Catching up, Due now, Coming next (its own h2 section), This season, Other vaccines. No About section (it's on Visit Prep). No "often given at the same visit" note.
  - **Schedule:** `ScheduleView`. **Timeline is the default**; List is alphabetical by vaccine name in the current language. A small left-aligned Timeline / List switch (icons, light style, so it doesn't look like the tabs), with `--space-5` (24px) below it. List is kept in the URL (`?view=list`), as is the tab, so both survive Dose Edit (dose links carry `?back=schedule[&view=list]`) and switching child.
  - No next appointment, pediatrician or questions sections: those live in Visit Prep (open questions also on Home).
- **Visit Prep (5) "About {name}"** (moved from the child page): delayed or alternate schedule, lived outside the US, medical conditions and past reactions, as a list just above Pediatrician; each only when answered, and the section only when there's anything. No sample child has the first three filled in; Ava has past reactions.
  - Received doses always show "Given <date>". The past-the-age-limit state only appears for doses that were never recorded (e.g. Sofía's rotavirus, by design in SPEC.md §5b). Wherever the child is known (Schedule tab, vaccine pages, Dose Edit, Add to record, record export…), that chip reads "{name} is past the age limit for starting this vaccine" (none received) or "…for the doses left in this series" (some received): the engine sets `DoseState.ageLimit` and `stateLabel(d, childName)` picks the text. It wraps on narrow screens. There is no separate notice under the vaccine name.
- **After Review Scan saves**, the child page shows a temporary toast ("3 doses added, 1 custom vaccine"), like Home's question/appointment toasts; closing it drops `scanAdded` from the URL.
- **Spacing:** `--space-6` (32px) between sections on the main screens (Home, child page, Visit Prep, Vaccines, Settings, guides); content within a section is closer (`--space-2`–`--space-3`). A title always lives in the same `<section>` as its content (labelled with `aria-labelledby`); guide Markdown is grouped into one section per h2.
- **Logo footer on every page** (`components/shell/BrandFooter.tsx`): a card with both logos, stacked on mobile, side by side on desktop. The logos aren't links (we only link to URLs AAP has given us).
- **Never black.** The darkest tone is charcoal (`--gray-900: #3d3d3d`), including text, primary buttons and shadows.
- **Font: Area.** `--font-sans` is `'Area Normal', 'Area', Arial, …`. Area is an Adobe Fonts face, so add a kit (or install it) to see it; otherwise Arial renders.
- **No all-caps text.** No `text-transform: uppercase`, and no all-caps placeholders or labels (acronyms like AAP are fine).
- **No language toggle before sign-in.** Screens 0 and 1a have no EN/ES toggle (overrides SPEC.md §6.0, §6.1a). Signed out, screens follow the browser's language. Signed in, the account's language applies, and the only switch is in Settings. Use the Spanish sample family to demo Spanish.
- **Screen 0 is a plain login card** (overrides SPEC.md §6.0's "what the tool does" lines and the two My Account buttons): "Log in", Email (*Required, no placeholder), a pill Continue button, and "Don't have an account? Register here." It never mentions the sample data. Mock: the email isn't sent or stored; Continue signs in to the sample account picked on /start, and Register starts the first-visit family.
- **First names only** for children everywhere (fixtures, labels: "Child's first name").
- **Birth month and year only.** The day of birth is never collected or shown ("Born May 2026"). Children added by hand in 1b give first name + month/year; it's stored as the 1st of the month with `dateOfBirthPrecision: 'month'`. A full date already on file (My Account) is kept unless the month/year changes.
- **Child Setup (1c) still cycles through every child** and is the child's profile page: the first name is the page title with "Child details" below; no editing banner and no "Filled in from your AAP My Account" line. It asks (all optional) whether the child is on a delayed or alternate schedule (`alternateSchedule`: yes/no/notSure), whether they've lived outside the US (`livedOutsideUs`: yes/no), and whether to get reminders for this child (`ReminderPrefs.perChild`, off by default; channels are chosen in Settings).
- **Dates computed from the birth date show month and year only** ("From March 2029", "Can be given from March 2027"), so the birth day never appears. Recorded dates (given, postponed to) keep the full date.
- **Dose Edit choices** (in order): Received, Delayed (illness or other reason), Not given, Non-medical exemption, Declined, Not sure. "Declined" (status `declined`, not in SPEC.md §5) means the caregiver chose not to have the dose: chip "Declined", treated like Not given (never overdue, not history). "Delayed" is the `postponed` status (SPEC.md's "Postponed"): it takes a new date and moves the following doses back by their minimum interval; the chip reads "Delayed to <date>". There's no separate "plan a date" choice any more. The `planned` status (`customTargetDate`) is still accepted from the API and shown as "Planned <date>", and Dose Edit opens such an entry as Delayed with that date.
- **Received as a custom vaccine** (not in SPEC.md): under Received, when the child has custom vaccines, a "Given as a custom vaccine (optional)" dropdown lists them all (name · date · country). Picking one fills in its date, shows a notice to check with the pediatrician that it counts, and saves `customVaccineId` on the dose. The dose counts as Received like any other. No extra question is added (the custom vaccine already added one).
- **"History" for overdue = a dose recorded as Received.** Not sure, postponed, planned, not given and exemption entries don't turn earlier "Not entered" doses into "Overdue".
- **Custom vaccines (4d) save back to the child page** (SPEC.md §4 says Visit Prep). The "how does it fit the schedule" question isn't automatic (SPEC.md §6.4d): a new entry has a checkbox "Ask my pediatrician how this vaccine fits the schedule", checked by default, that adds it to Visit Prep. Scan's "Make custom" still adds it.
- **Scan "Make custom" happens in place** in Review Scan (SPEC.md §6.4c says → 4d): the item is saved with the others as a custom vaccine, with its auto-question, so the review isn't lost. Edit it afterwards from Other vaccines.
- **Mock OCR fits the fixture card to the scanned child**: printed dates move by whole months to fit the child's birth date (day numbers kept, so "03/04" stays ambiguous and every flag type appears). Scanned doses are numbered by date among recorded doses, capped at the series length.
- **Guides** are Markdown in `content/guides/[slug].[locale].md` (front matter `sample: true`; no longer shown as a "Placeholder text…" chip). The guide page reads both languages at build time (`lib/guides.ts`) and renders them with `lib/markdown.ts` + `components/guides/Markdown.tsx`: headings, paragraphs, lists, bold, links only, never raw HTML. Link forms: `/…` (in-app), `app:scan|add|custom` (that screen for the selected child), `https://…` (new tab). Titles for lists are in messages `guides.titles.*`. Only link to external URLs AAP has given us; the registry list and costs link are left for AAP.
- **Vaccines & Guides (6):** the page title is "Vaccines & Guides" (the tab bar still says "Vaccines"), with WAI-ARIA tabs: Vaccines (default: search + A–Z) and Guides (the guide list). The tab is in the URL (`?tab=guides`); a guide's "← All guides" returns to the Guides tab.
- **"No child" on the Vaccines tab** (SPEC.md §13 default) hides the child module on vaccine pages; Visit Prep is one child at a time.
- **Edit Child (3)** was built in milestone 8 (no milestone in §12 names it). Birth month + year only; a birth-date change that makes recorded doses look wrong lists them and asks for "Save anyway".
- **Settings has no child selector** (§13 open question); it lists every child. Reminders: SMS (US numbers) / email with validation, lead time 1 week / 2 weeks / 30 days, per child, live preview. Delivery is mocked: in dev, "Send reminders now" logs messages (what's due + window, pediatrician's number, deep link) to the Reminder log via `/api/__dev/reminders`; nothing is sent.
- **Export** is `/child/[id]/record`: a print view and a PDF built in the browser with `pdf-lib` (`lib/export/recordPdf.ts`), both labeled "Personal record, not an official immunization record".
- **Sample free text has Spanish versions** (`textEs`, `priorReactionsEs`, `doseNotesEs` in the fixtures) used for Spanish-language sample accounts. In dev, a missing translation renders as `⟦missing: key⟧` (scenario 12 checks for it).
- **Loading, error, offline and not-found states (milestone 9)** live in `components/states/`. Screens gate their queries with `useGate(queries, waiting)` (skeleton while loading; "We couldn't load this" + Try again on failure) instead of `return null`; AppShell does the same for the account and child list and shows `OfflineBanner`. A missing dose, custom entry or used scan shows `NotFoundState` with a link back to the child. `app/error.tsx` catches crashes; `app/global-error.tsx` is a bilingual last resort.
- **Fault injection (dev mock only):** `PUT /api/__dev/fail { paths: [...] }` makes GET requests whose path contains any of them return 500, so error states can be checked (`e2e/states.spec.ts`). The list is kept in sessionStorage across reloads (mock config, no child data); send `paths: []` to clear.
- **Touch targets:** standalone text links use the global `.target-link` class (44px tall); `linkButton` / `dangerLink` have a 44px minimum width. `e2e/keyboard.spec.ts` measures every control on the main screens.
- **Visit Prep pediatrician:** the phone number itself is the `tel:` link (no Call button). The print button says "Print".
- **Visit Prep questions:** "Add a question +" sits on the "Questions and notes" title line, at the right, and opens Home's Question popup (`QuestionDialog`) with the page's child picked; saving shows a toast. No question form on the page.
- **Answers and Past questions (5a, not in SPEC.md):** a question can have an optional `answer` (the caregiver's note of what the pediatrician said): "Add answer" / "Edit answer" under the question on Visit Prep, shown as "Answer: …". Resolved questions aren't listed on Visit Prep any more; they're on `/visit-prep/past?child=` ("Past Questions for {name}", grouped like Visit Prep, with answers; unchecking reopens one). It has "← Back" at the top (history back, else Visit Prep), no tab of its own (Visit Prep stays active), and the switcher. Linked from Visit Prep ("Past questions (n)" under the questions) only. Home's Open Questions rows also have "Add answer" / "Edit answer" under the question (outside the tap-to-check label). Maya's sample data has one answered, resolved question.
- **Spanish uses formal usted** throughout (messages, guides).
- **Formatting:** Prettier with `--single-quote --print-width 160` (there's no config file; don't run Prettier with its defaults).
- **Dev entry flow.** Logged-out visitors land on `/start` ("Choose sample data", dev + mock only, not an IA screen) → Enter tool → `/login` (screen 0: Log in / Create account). Log in signs in to the chosen sample account; Create account uses `new-family`.

## Project map

- `lib/routes.ts`: the §3 route table (screen number, page vs. form, tab, selector). The shell reads it; keep it in sync with `app/`.
- `lib/api/`: `schemas.ts` (Zod contract), `client.ts` (the only `fetch`), `endpoints.ts`, `hooks.ts` (TanStack Query)
- `lib/data/`: Zod schemas + parsed access for `data/` seed files
- `lib/schedule/`: the pure schedule engine (`computeChildSchedule`, `checkDoseDate`, `dosesDueAt`) and `useChildSchedule` (runs it on the client). Conventions: a dose is `dueNow` from `dob + window.start` through the day before `dob + overdueFrom`; a postponed previous dose pushes the next by its minimum interval and gives it at least a month before overdue; missing doses past `catchUpThrough` (or rotavirus's max age) are `noLongerRecommended`; flu/COVID/RSV/MenB are reported in `seasonal` and never affect status. Tests: `tests/schedule.test.ts`, one block per SPEC.md §7 rule plus the four sample children.
- `lib/services/`: interfaces for My Account, OCR and notifications. Mocks are in `mocks/services.ts`
- `mocks/`: MSW handlers, fixture seeding (`db.ts`), browser worker (persists to localStorage, dev only) and Node server (tests). The dev banner's "Reset mock data" reseeds.
- `components/record/`: Add to Record (4a), Dose Edit (4), Custom Vaccine (4d). `lib/search/vaccines.ts`: catalog search (both languages, accents, typos). `lib/validation/dose.ts`: Dose Edit and Custom Vaccine checks.
- `components/scan/`: Scan a Record (4b) and Review Scan (4c). `lib/scan/`: printed-date reading, review rules (flags, blockers, commit) and the in-memory photo store (never browser storage).
- `components/visitPrep/` (5), `components/vaccines/` (6, 6a), `components/guides/` (7). Visit Prep's "Print" button uses print styles in `app/globals.css` (`.no-print`, `.print-only`).
- `app/settings/` (8), `components/child/EditChildScreen.tsx` (3), `components/child/RecordExportScreen.tsx` (export), `lib/reminders.ts` (what a reminder covers), `lib/validation/contact.ts` (phone / email).
- `components/home/`, `components/child/`: Home (1) and the child page (2). `components/schedule/`: `ScheduleView` (Timeline default / List), `DoseChip` (icon + text + pattern) and `useScheduleText` (vaccine names, age windows, state labels).
- `components/shell/`: AppShell (brand header), TabBar, ChildSelector (pill switcher), EditingBanner, BrandFooter, StatusPill, SampleDataBanner
- `messages/en.json`, `messages/es.json`: all UI copy

## Next.js 16 notes

- Cache Components is on. Everything under `components/providers/Providers.tsx` renders browser-only (`use(browser())`), because data comes from the browser-side mock API. For that reason the root layout and every `page.tsx` export `instant = false`; add it to new pages.
- `devIndicators` is off in `next.config.ts`: Next's "N" badge sat on the Home tab and blocked taps (errors still show in the dev overlay).
- MSW starts in `instrumentation-client.ts` (browser bundle only), because `msw/browser` can't be bundled for the server.
- Next keeps recently visited routes mounted but hidden (Activity), so give radio groups and other document-global names a `useId()`, and reset transient UI such as menus on hide.
- In a page that's keyed by a route param (e.g. `[childId]`), read the param from the page's own `params` prop (pass the promise down and `use()` it), not `useParams()`: `useParams()` follows the current URL, so a hidden copy of the previous page re-renders as the new one.
- In Playwright, hidden copies of earlier pages are still in the DOM. Scope text/label/test-id matchers with `.filter({ visible: true })`, and don't match `role="alert"` (Next's route announcer uses it).
- Route guards live in `lib/guards.ts` (pure, unit-tested) and run in `AppShell`. Child drafts from 1b have a blank name and no DOB until set up in 1c; use `isSetUp()` before showing a child anywhere else.
